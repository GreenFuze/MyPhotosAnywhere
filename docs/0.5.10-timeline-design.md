# MPA 0.5.10 timeline design

Status: implementation design; automated and device acceptance pending.

## Existing representation and identity

Room schema 9 stores local/indexed media in `photos` and source-scoped remote entries in `cloud_photos`. Local identity is `photos.id`; remote identity is `cloud_photos.key` (binding plus remote ID). A verified `cloud_photos.photoId` association connects representations. Filename similarity does not establish identity.

`MainActivity.LibraryScreen` currently filters and sorts two full lists, then concatenates the local and remote sections. That presentation boundary causes the split chronology; it does not require a new persistent media table.

## Read-only projection

Use one parameterized `UNION ALL` projection with canonical keys `photo:<id>` and `cloud:<key>`. Suppress a remote representation only when its existing `photoId` points to an existing local row, including when that local row is excluded by archive or another filter. Preserve unlinked source entries. Apply source, tombstone, archive, Favorites, album, person and edit visibility before paging.

For local entries, derive effective time from stored capture time, linked cloud capture time, then import time. Prefer the exact original source binding and remote ID among linked capture timestamps, then cloud-key order. Timestamp derivation must not depend on the active source filter or connection health. Remote entries use capture time, valid Drive modification time, then Unknown date. Record provenance in the projection. Sort known times descending and canonical keys ascending, with unknown dates last. Do not rewrite persisted metadata.

This adds no entity, table, column or migration. Confirm generated schema 9 and its identity hash remain unchanged.

## Paging and gallery continuity

Use exact stable Paging 3.5.2 (owner approved October 12, 2026) with bidirectional keyset paging with deterministic time/key cursors. Configuration: 60-item pages, 90-item initial load, prefetch 18, retained-page budget 300, no placeholders. Keep full-library observation confined to legacy destinations. Resolve actions by stable IDs.

Verify original file availability off the main thread for Offline filtering. Continue scanning bounded candidate batches when files are missing, rather than treating a rejected batch as the end of the dataset.

Date headings use device-local days. Preserve identity plus pixel offset across invalidation, imports, navigation, rotation and timezone changes. Jump to date seeks through the repository. An anchor that disappears requires explicit recovery; it must never select another photo accidentally.

## Viewer sequence

Open the selected preview immediately. Build a disposable private SQLite index of the originating query's ordered identities using a short source snapshot and bounded batches. Close the source transaction after preparation. Keep only nearby resolved media in memory; load adjacent entries by session ordinal. New imports must not change that sequence.

A verified cloud-to-local transition updates resolution within the same session entry. Unavailable entries retain their identity and recovery state. Preserve existing renderer, verified downloads, cache leases, gestures, cancellation and video lifecycle controls. Retain sessions across rotation; process recreation reopens the saved identity/context or returns safely to the anchored gallery.

## Verification and release gate

Mixed-source identity/visibility tests, bidirectional paging, seek/date boundaries, concurrent imports, representation transitions, anchors, offline checks, cancellation, preservation and 10,000/100,000-item Android measurements are required. Desktop SQLite feasibility timings are research only and do not establish Android performance.

Publication requires checks with no unresolved warnings other than the explicitly approved AGP 9.4.1 / Gradle 9.8.1 upstream deprecation and native tests on API 29, 35 and 37.0 for one immutable application revision, followed by independent APK/version/checksum/signing verification. S23 Ultra acceptance and the previously reported JPEG crash remain unverified.

## Snapshot concurrency and validation

Viewer indexing uses Room's reader connection and a deferred read transaction. It does not reserve the library's writer connection while copying identities. The private disposable index retains 60-row write batches and an in-memory rollback journal; the library's journal and schema are unchanged. On API 28+, the source cursor uses forward-only filling and an 8 MiB maximum window; API 26/27 retain the platform window. Closing the cursor releases its window.

The native 100,000-item fixture performs an import write after the private index has started growing. It requires the write to finish while preparation is still active and verifies that the session retains its earlier ordering. This assertion, pixel-offset restoration, and the complete API 29/35/37 matrix must pass on the final revision before publication.

Espresso is explicitly pinned to stable 3.7.0. Compose otherwise resolved an older transitive 3.5.0, whose InputManager reflection fails on API 37 before UI assertions can execute. Existing assertions remain unchanged.

## Local continuity evidence

The full local API 35 run passed 43 native tests, including concurrent import writes during snapshot preparation and viewer return after activity recreation. The 226 host tests and lint also passed. These checks used the local validation signer and an older local emulator; they do not satisfy the final CI release gate.

Before/after screenshots and semantics diagnostics showed the same photo at window Y=656 px and the same grid origin at Y=231 px. Recreation moved the Compose root by the 63 px status-bar inset. The continuity test therefore compares window coordinates, retains its 3 px tolerance, and additionally checks the offset within the grid. Both screenshots remain in native test artifacts. The coordinate frames follow the [Compose SemanticsNode API](https://developer.android.com/reference/kotlin/androidx/compose/ui/semantics/SemanticsNode).
