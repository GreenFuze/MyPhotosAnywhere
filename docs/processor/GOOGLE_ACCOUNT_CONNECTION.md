# Processor Google connection candidate

The product Google adapter uses exact Google.Apis.Auth 1.77.0 and PKCE S256, with a random 256-bit request state independently checked on the loopback reply. Browser consent opens the user's system browser. The listener binds to 127.0.0.1 with an ephemeral port; cancellation and Exit join the SDK callback owner. A browser process belongs to the user and is not terminated by Processor shutdown.

`GoogleCredentialDataStore` accepts exactly its connection ID and TokenResponse type. Its bounded versioned token record resides only in the native credential vault. A refresh response may omit its unchanged refresh token or scope; these are retained only from the same connection. An expired access token is kept with its refresh grant and original issue time. Invalid/incomplete/scope-reduced responses do not overwrite a valid record; corrupt/unknown/duplicate record fields fail explicitly. Clear affects exactly this connection, never the vault or other Google applications.

`GoogleAccountConnection` serializes and owns the SDK flow, browser callback, HTTP identity check and cancellation. The public surface returns verified Drive permission IDs and display fields, never raw credentials. HTTP account reads are fixed to the official HTTPS Drive about endpoint, bounded to16KiB, disallow redirects and refresh once for401. Temporary HTTP failures preserve credentials. No source scan, upload, trash or original mutation occurs in these connection methods.

Account reconnection must use a **new pending connection ID**, with the existing permission ID captured as the expected identity. Promote the new connection only after verification. Existing bindings/jobs continue referring to the stable account permission ID. The adapter will not let an interactive retry overwrite an existing connection's credential before identity verification. Wrong-account results fail and do not promote source bindings; pending credential cleanup belongs to the setup transaction/recovery owner. Local disconnect forgets that connection's credential; it does not revoke Google's shared client grant or delete media.

Desktop OAuth client configuration is injected by packaging from the private authorized configuration. It is an installed-client identity, not a user grant, and is kept out of public source under Google's client-credential publication policy. Refresh grants, private callback URLs and consent codes are never build assets. No production grant has yet been migrated by this adapter increment.

Nine synthetic product tests cover retained expired grants, omitted refresh fields, exact connection isolation, invalid/corrupt records, real loopback matching/mismatching state, PKCE request construction, canceled callback closure, joined Exit, read-only stable identity and preserved credentials on wrong-account/network failures. They make no Google network requests. Cross-platform CI and actual product UI/live-refresh acceptance remain separate required evidence. The earlier private probe grant and elapsed-time observations remain intact.

Primary references: [Google installed-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Google OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies), [Drive about.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/about/get).

## Setup coordinator

ProcessorAccountService owns each connection attempt from durable pending creation through account verification and atomic promotion. It borrows the single shared background SQLite coordinator and native vault, owns/disposes the active Google connection, and joins actual cancellation before Exit. Failed attempts remain resumable under the same captured ID. Wrong-account results do not promote or schedule existing credential deletion. A durable cleanup row is checked before vault deletion and acknowledged only afterward; locked-store failures retain it for retry. Retired cleanup identities cannot be reused for a new pending connection. Five service tests exercise promotion/reconnection, failed-only setup resume, wrong-account preservation, locked cleanup retry and held-owner cancellation/Exit.

## Engine read ownership and credential retirement

Foreground web reads and background discovery share one engine-owned reader service through ProcessorAccountService. Read connections remain private, bounded by the account limit, and serialize callbacks with retirement. Disconnect or promotion first changes the durable account revision. Credential cleanup then joins any old read/refresh and its actual connection disposal before deleting the native-vault record or acknowledging the cleanup journal. Later reads resolve the current account revision instead of reopening a retired connection. A failed disposal or canceled cleanup retains the journal for retry. Exit cancels and joins both setup and read ownership.

Ten local account-service tests pass, including held refresh/save, held disposal, reconnect, canceled cleanup, failed disposal retry and Exit. Google20/Web11 regression tests and the strict desktop composition build also pass locally. Native validation of this increment remains required. No grant, scope, browser consent or original media was changed by these synthetic tests.
